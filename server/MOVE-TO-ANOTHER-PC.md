# 다른 Windows 11 PC로 서버 옮기기

## 복사할 파일 하나

`server/artifacts/portable/StudyServer.exe`

이 개인용 EXE에는 Firebase 서버 계정 JSON과 NEIS·AI 키가 내장돼 있다. 새 PC에서 키 입력, 별도 런타임 설치, 백업 복원이 필요 없다. 기존 학습 DB는 가져오지 않고 새 DB로 시작한다. 로그인 계정은 기존 Firebase Auth 계정을 그대로 쓴다.

이 파일에는 실제 비밀 키가 들어 있다. 공개 저장소나 다운로드 링크로 배포하지 않고 본인 서버 PC로만 옮긴다. EXE 안의 키는 추출될 수 있다. 기존 PC의 `settings.protected` 파일을 복사할 필요는 없다.

## 1. 새 PC의 내부 IP 확인

1. 새 PC를 서버로 사용할 공유기에 유선으로 연결한다.
2. Windows에서 **Win+R → `cmd` → Enter**를 누른다.
3. `ipconfig`를 입력한다.
4. 연결된 **이더넷 어댑터**의 **IPv4 주소**와 **기본 게이트웨이**를 적는다. Tailscale·WireGuard 등 가상 어댑터 주소는 사용하지 않는다.

현재 새 서버 PC에서 확인한 IPv4는 `192.168.0.200`이다. 다른 PC로 다시 옮긴다면 해당 PC의 실제 IPv4로 바꾼다.

## 2. 새 PC의 주소를 공유기에 고정 할당

현재 ipTIME 공유기 관리 주소는 `http://192.168.0.1`이다. 다른 공유기라면 위에서 확인한 기본 게이트웨이를 브라우저 주소창에 입력한다.

1. 관리 화면에 로그인한다.
2. **DHCP 서버 / DHCP 고정 할당 / 수동 등록** 화면을 찾는다. 펌웨어에 따라 이름과 메뉴 위치가 다르다.
3. 접속된 기기 목록에서 새 PC의 현재 IPv4와 일치하는 기기를 고른다.
4. 그 PC의 MAC 주소에 현재 IPv4를 고정 할당하고 저장한다. MAC을 직접 입력해야 한다면 새 PC에서 `ipconfig /all`을 실행해 같은 이더넷 어댑터의 **물리적 주소**를 확인한다.
5. 기존 PC의 `.10` 주소 예약은 그대로 둬도 된다. 두 PC에 같은 주소를 중복 할당하지 않는다.

## 3. 기존 포트포워딩의 전달 대상 변경

현재 ipTIME에서는 `http://192.168.0.1/ui/portforward`로 포트포워딩 화면을 열 수 있다. 메뉴로 찾는 경우 **NAT/라우터 관리 → 포트포워드 설정** 또는 **포트포워딩**을 찾는다.

최신 EXE는 **TCP 443만 사용**한다. 기존 `STUDY-HTTPS` 규칙을 아래처럼 저장한다. 새 PC에서 다른 프로그램이 사용 중인 80 포트는 STUDY가 건드리지 않는다. 이전에 만든 `STUDY-HTTP`(80) 전달 규칙은 사용 안 함으로 바꾸거나 삭제한다.

| 기존 규칙 이름 | 프로토콜 | 외부 포트 | 내부 IP | 내부 포트 |
|---|---|---|---|---|
| STUDY-HTTPS | TCP | 443 | 192.168.0.200 | 443 |

HTTPS 규칙의 사용/활성화 상태가 켜져 있는지 확인한다. 다른 공유기에 처음 설정하는 경우에도 위의 한 규칙만 추가한다.

기존 WireGuard·Tailscale UDP 규칙은 수정하지 않는다. DMZ는 켜지 않는다. 내부 API `18081`과 DB `15432`는 포트포워딩에 추가하지 않는다.

## 4. DNS 변경이 필요한지 확인

- **기존과 같은 공유기·인터넷 회선:** 공인 IP가 그대로라면 Spaceship DNS를 변경할 필요가 없다. 포트포워딩 대상 PC만 바꾸면 된다.
- **다른 장소·다른 인터넷 회선:** 새 공유기에서 위 HTTPS 규칙을 설정하고, Spaceship의 `junhyuk.site` DNS 관리에서 **A / api.study** 값을 새 장소의 공인 IPv4로 변경한다. 공인 IPv4는 EXE 창에 표시된다. 기존 값은 `39.124.233.99`다.

DNS의 `@`, `study`, `word` GitHub Pages 레코드는 유지한다. API 주소는 계속 `https://api.study.junhyuk.site`이므로 웹앱을 다시 배포하거나 로그인 계정을 다시 만들 필요는 없다.

## 5. 새 EXE 실행 및 외부 확인

1. 기존 PC의 STUDY 서버 창을 닫는다.
2. 새 PC에서 위 개인용 EXE를 실행한다. 키 입력 없이 새 PC용 설정과 DB를 만들고 시작한다. 기존에 설정된 서버가 있으면 그 설정과 DB는 유지한다.
3. Windows 권한 확인이 나오면 **예**를 선택한다. 프로그램이 Caddy에 한해 TCP 443 방화벽 규칙을 설정한다. 이전 80·443 규칙이 있으면 자기 규칙만 443으로 축소한다.
4. 공유기 전달과 DNS가 맞으면 TLS-ALPN 방식으로 443 포트에서 HTTPS 인증서를 발급한다. 80 포트는 인증서 발급이나 HTTP 리다이렉트에 사용하지 않는다. 공개 연결은 10초마다 다시 검사하므로 인증서 발급 후 상태가 자동 갱신된다.
5. 휴대폰의 **Wi-Fi를 끄고 모바일 데이터**에서 `https://api.study.junhyuk.site/health`를 연다.
6. JSON 응답과 서버 창의 **운영 중** 표시를 확인한다. 웹앱은 Ctrl+Shift+R로 새로고침하고 기존 계정으로 로그인한다.

창을 닫으면 서버가 종료된다. Pages 화면과 Firebase 로그인은 서버가 꺼져 있어도 열리지만 기록·학교·AI 요청은 자체 서버가 실행돼 있어야 동작한다.

## 연결이 안 될 때

| 증상 | 확인할 항목 |
|---|---|
| EXE에 이미 실행 중이라는 안내 | 같은 PC에서 실행 중인 이전 STUDY 서버 창을 먼저 닫는다. |
| DB 초기화 중 invalid byte sequence for encoding UTF8 | PostgreSQL에서 한글 데이터 경로 제약이 확인됐다. 현재 기본 데이터 위치는 Windows 사용자의 LocalAppData 아래다. 해당 Windows 사용자 폴더가 한글이면 영문 사용자 폴더의 Windows 계정에서 실행한다. EXE를 둔 폴더와 DB 데이터 폴더는 별개다. |
| 로컬 실행 중 · 외부 연결 확인 필요 | 새 PC의 실제 IPv4와 두 규칙의 내부 IP, Windows 권한 확인 승인, DNS A 값을 확인한다. |
| 새 장소에서 포트를 열어도 외부 시간 초과 | 공유기 WAN IPv4와 실제 공인 IPv4가 같은지 확인한다. 다르면 상위 공유기 또는 통신사 공유 주소 문제를 먼저 해결해야 한다. |
| 휴대폰 모바일 데이터에서는 되지만 집 Wi-Fi에서 실패 | 공유기의 NAT 루프백/헤어핀 NAT 지원과 내부 DNS 설정을 확인한다. |
| 화면은 열리지만 기록·학교·AI가 연결 오류 | API health가 먼저 응답해야 한다. 웹앱은 Firebase 데이터 서비스로 우회하지 않는다. |
