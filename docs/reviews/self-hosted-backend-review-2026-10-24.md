# 자체 서버 이전 검토

검토일: 2026-10-24. 현재 작업 폴더의 소스·설정과 Firebase 공식 문서를 기준으로 검토했다. 운영 환경이나 데이터는 변경하지 않았다.

## 판단

**직접 운영하는 서버로 이전할 수 있다.** 다만 현재 Firebase는 로그인, DB, 서버 함수 세 역할을 수행한다. 설정의 서버 주소만 교체해서 전체 이전할 수 있는 구조는 아니다.

현재 구조에서는 **서버 함수 → DB → 인증 순서의 단계적 이전**이 가장 현실적이다. 최종적으로 Node.js API 서버와 PostgreSQL, 자체 인증으로 전환할 수 있다. 이는 설계 제안이며 새 서버의 성능이나 호환성을 실증한 결과는 아니다.

| 방식 | 자체 운영 범위 | Firebase 잔존 | 상대적 변경 규모 |
|---|---|---|---|
| 서버 함수만 이전 | 학습·친구·학교·AI API, 정기 작업 | Auth와 Firestore | 중간 |
| 서버 함수와 DB 이전 | API와 PostgreSQL | Auth, 외부 단어앱 인증 연동 | 큼 |
| 전체 이전 | API·DB·로그인·메일·정기 작업 | STUDY 내부는 제거 가능. 외부 단어앱의 Firebase 의존은 별도 처리 | 가장 큼 |

첫 번째 방식은 기존 사용자와 DB를 유지하며 서버 실행 환경부터 바꿀 수 있다. 하지만 Firestore 사용 요금과 Firebase 인증 의존은 남는다. DB까지 직접 소유하려는 목적이라면 두 번째 단계 이상이 필요하다.

브라우저 카메라 분석은 현재 문서·구조상 기기 내 처리이므로, 백엔드 이전을 위해 영상을 서버로 전송하거나 영상통화 서버를 추가할 필요는 없다. 확인한 앱 코드에서는 Firebase Storage·Realtime Database를 사용하는 근거를 찾지 못했다. 설정의 `storageBucket`·`messagingSenderId` 존재만으로 해당 서비스 사용을 판단하지 않았다.

Serena 프로젝트 활성화는 수행했지만 활성 언어 서버가 없어 심볼 추출은 사용할 수 없었다. 필요한 코드 범위와 참조를 직접 검색해 검토했다.

## 제안하는 자체 서버 구성

- 기존 정적 웹 화면 → HTTPS API 서버(Node.js) → PostgreSQL.
- 리버스 프록시에서 TLS, API 도메인, 스트리밍 연결을 처리한다. 예를 들어 웹은 기존 `study.junhyuk.site`, API는 별도 서브도메인을 사용한다.
- 사용자 프로필·활성 세션은 인증된 SSE/WebSocket 연결로 전달한다. 스터디룸은 기존의 화면별 주기 조회를 우선 유지해 변경 범위를 줄인다.
- 정기 작업 프로세스는 1분마다 실행하고, 중복 실행에도 안전하게 만든다. 여러 서버로 확장하면 DB 잠금 등으로 작업 실행권을 관리한다.
- 초기에는 캐시·요청 제한·작업 잠금을 PostgreSQL로 구현할 수 있다. Redis 필요성은 실제 부하를 보고 결정한다.
- DB 백업·복원, 서버 자동 재시작, 오류·지연 모니터링, 비밀 키 관리가 자체 운영 범위에 추가된다.

PostgreSQL은 현재의 사용자·세션·집계·화폐 원장·친구 관계를 트랜잭션과 제약 조건으로 관리하기 위한 제안이다. Firestore와 문법만 바꿔 호환되는 저장소는 아니므로 서비스별 DB 접근을 분리해야 한다.

## 반드시 유지해야 하는 동작

1. **중복 적립 방지:** 세션 종료의 재시도·동시 요청·만료 정리가 겹쳐도 학습시간, 통계, 랭킹, Focus Time을 한 번만 적립해야 한다. 현재 종료 처리는 트랜잭션에서 완료 여부를 다시 확인한다. 새 DB에서도 잠금과 고유 제약 등으로 보장한다.
2. **학습시간 계약:** 서버 기준 시각, 연결 유효기간, 일시정지, 카메라·단어 학습 중복 방지, 날짜 경계와 순서가 늦은 요청의 처리를 보존한다. 서버 장애 후 복구했다고 연결이 끊긴 시간을 자동 인정해서는 안 된다.
3. **AI 예산:** 생성 전 예약, 동시 요청 제한, 성공·실패·취소 정산, 월별 예산과 일별 횟수를 원자적으로 처리한다. 프로세스 재시작 후 남은 예약도 복구할 정책이 필요하다.
4. **접근 권한:** 현재 `firestore.rules`의 본인 기록 조회, 같은 학교 랭킹 조회, 최대 50개 조회, 클라이언트 쓰기 금지에 대응하는 검사를 API에 구현한다. Admin SDK를 쓰는 자체 서버도 요청마다 권한 검사가 필요하다.
5. **단어앱 호환성:** 외부 앱이 기존 함수 이름·주소·custom token을 이용하는 경로를 확인하고 함께 배포한다. STUDY 저장소만 수정해서 외부 앱까지 이전이 끝났다고 판단할 수 없다.

## 이전 순서

1. **인터페이스 정리:** 서버 호출 세 경로를 공통 클라이언트로 모으고, Firebase SDK 응답·오류와 화면 로직 사이에 변환 계층을 둔다. 서버 서비스 로직은 HTTP 처리에서 분리한다.
2. **API 서버 이전:** 우선 Firebase Auth·Firestore를 유지한다. 자체 API가 Firebase ID 토큰을 검증하고 기존 서비스 로직을 실행하게 한다. Callable의 자동 인증 처리를 대체하고 AI 스트리밍도 연결한다.
3. **브라우저 DB 직접 접근 제거:** 프로필·세션 구독, 통계·랭킹 조회를 자체 API로 옮긴다. 이 단계가 끝나면 화면을 DB 구현과 분리할 수 있다.
4. **DB 이전:** 사용자와 하위 컬렉션, 랭킹, 화폐 원장, 친구·초대·방·코드, 계획, AI 사용량·예약, NEIS 캐시, 계정 연결, 세션 lease 등 실제 사용 데이터를 목록화한다. UID와 문서 식별자를 보존하고 필요한 집계·검색 인덱스를 만든다.
5. **전환 검증:** 별도 환경에서 데이터 건수·합계·참조 관계와 핵심 동작을 비교한다. 최종 전환에는 짧은 쓰기 중지와 최종 동기화 방식을 우선 검토한다. 근거 없이 두 DB에 병렬로 쓰는 방식을 도입하지 않는다.
6. **인증 이전:** 완전 독립이 목표일 때 마지막으로 진행한다. 기존 계정 ID 매핑, Google 로그인, 이메일 발송, 토큰·세션 만료, 단어앱 복원을 검증한다.

전환 후 새 DB에 쓰기가 발생하면 이전 Firebase로 주소만 되돌리는 것으로 데이터가 복구되지 않는다. 되돌릴 시점과 데이터 재동기화 방식을 전환 전에 정해야 한다.

## 운영·비용 판단

현재 정보만으로 자체 서버가 더 저렴하거나 빠르다고 확정할 수 없다. 서버 사양·설치 장소·회선·동시 사용자 수·실제 Firebase 청구·DB 크기·읽기/쓰기량을 확인하지 않았다.

특히 학습 상태의 주기적 동기화가 있으므로 단순 가입자 수보다 동시에 활성화된 학습 세션 수가 부하를 좌우한다. 부하 측정에는 세션 동기화 요청, 스터디룸 조회, AI 스트리밍 동시 연결을 함께 포함해야 한다. AI와 NEIS 등 외부 서비스 의존은 서버 이전 후에도 남는다.

집의 PC·NAS라면 외부 HTTPS 접속, 통신사 NAT·포트 제한, 전원·절전·재부팅, 회선 장애를 확인해야 한다. VPS라면 인스턴스·DB 저장공간·백업 비용과 직접 운영 시간을 합산해 비교한다. 특정 CPU·RAM이나 월 비용은 측정 없이 제시하지 않는다.

## 검증 범위와 후속 확인

이번 검토는 소스와 설정에 대한 정적 검토다. 서버 교체, 운영 데이터 조회·반출, 배포 또는 새 서버 성능시험은 수행하지 않았다. 코드 변경이 없어 테스트를 재실행하지 않았으며, 기존 테스트 성공 여부를 이번 검토의 근거로 주장하지 않는다.

기존 `tests/firebase.test.mjs`, `tests/room-live.test.mjs`, `tests/word-link.test.mjs`는 새 서버 검증 시 옮겨야 할 동작의 근거로 활용할 수 있다. Firebase 규칙·SDK·에뮬레이터에 묶인 부분은 새 API·DB 통합 테스트로 교체해야 한다.

구체적인 구현 규모·운영 구성을 결정하려면 **서버 종류와 사양, 예상 동시 사용자 수, Firebase 완전 제거 여부**가 우선 필요하다. 단어앱 저장소와 운영 계정·DB 규모는 후속 조사 대상이다.

## 공식 문서로 확인한 사항

- Firebase Admin SDK는 자체 서버에서 사용할 수 있다. 따라서 API 서버만 먼저 이전하는 방식이 가능하다. [Admin SDK 설정](https://firebase.google.com/docs/admin/setup)
- 자체 백엔드는 클라이언트의 Firebase ID 토큰을 검증해 사용자를 확인할 수 있다. [ID 토큰 검증](https://firebase.google.com/docs/auth/admin/verify-id-tokens)
- Callable에는 별도 요청·응답·인증 규약이 있다. 일반 HTTP API로 바꿀 때 SDK 호출을 함께 수정하거나 호환 규약을 구현해야 한다. [Callable 프로토콜](https://firebase.google.com/docs/functions/callable-reference)
- 사용자 내보내기에서 비밀번호 해시·salt를 얻으려면 별도 권한이 필요하다. 새 인증 시스템에서 기존 해시를 검증할 수 있는지도 확인해야 하므로 기존 비밀번호 유지까지 자동으로 보장되지는 않는다. [사용자 관리와 내보내기](https://firebase.google.com/docs/auth/admin/manage-users)
- Firebase Emulator Suite는 성능·보안을 위한 운영용 서비스가 아니다. 에뮬레이터를 서버에 상시 실행하는 방식으로 운영 Firebase를 대체하는 것은 제외한다. [Emulator Suite 안내](https://firebase.google.com/docs/emulator-suite)
